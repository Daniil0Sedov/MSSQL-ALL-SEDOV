# Список спорных решений

## 1. Поиск по курсам: PostgreSQL FTS vs OpenSearch/Elasticsearch

**Аргументы за PostgreSQL FTS:** меньше инфраструктуры, единый источник запросов, согласованность ближе к данным.

**Аргументы за OpenSearch/Elasticsearch:** лучше опечатки, ранжирование, синонимы и фасеты; поиск можно масштабировать отдельно.

**Решение:** OpenSearch/Elasticsearch как производный индекс. PostgreSQL FTS оставить fallback для MVP или малого каталога.

## 2. Контент курсов: MongoDB vs PostgreSQL JSONB

**Аргументы за MongoDB:** естественно хранит глубокую неоднородную структуру и допускает гибкое развитие схемы.

**Аргументы за PostgreSQL JSONB:** меньше систем, проще транзакции с правами и публикацией.

**Решение:** MongoDB для черновиков и структуры контента; PostgreSQL для прав и реестра публикаций. Публикация — через outbox.

## 3. Рекомендации: пакетный ClickHouse + Redis vs графовая БД

**Аргументы за ClickHouse + Redis:** проще в эксплуатации, использует уже имеющиеся события и обеспечивает быструю выдачу.

**Аргументы за графовую БД:** лучше выражает многозвенные связи и онлайн-обходы при усложнении алгоритма.

**Решение:** начать с ClickHouse + Redis; рассмотреть графовую БД только при доказанной потребности.

## 4. Сессии: server-side Redis vs stateless JWT

**Аргументы за server-side Redis:** немедленный отзыв, единый TTL и контроль активных устройств.

**Аргументы за JWT:** меньше обращений к Redis и удобнее для межсервисного взаимодействия, но сложнее отзыв и смена ролей.

**Решение:** server-side сессии/allow-list в Redis; короткоживущий access token возможен дополнительно.

# Storage architecture v1 — Data Placement Map

## Решения

- Пользователи: PostgreSQL; Redis для кэша профиля и прав.
- Сессии и токены: Redis с TTL; audit-события при необходимости в ClickHouse.
- Курсы и уроки: MongoDB для структуры контента, PostgreSQL для прав и публикации; Redis и поисковый индекс — производные.
- Прогресс: PostgreSQL; Redis для краткого кэша состояния; события в ClickHouse.
- Поиск: OpenSearch/Elasticsearch как производный индекс опубликованных курсов.
- Форум: PostgreSQL; Redis для горячих тем и счётчиков.
- Логи действий: ClickHouse через поток событий/батчи.
- Аналитика и отчёты: ClickHouse, материализованные представления и витрины.
- Рекомендации: расчёт в ClickHouse, предрассчитанная выдача в Redis.

# Синхронизация и потоки данных

## Потоки по сущностям

- **Пользователи:** PostgreSQL → transactional outbox / CDC → Redis. При смене профиля или роли событие инвалидирует и заново заполняет кэш. Проверка прав при критичном действии обращается к PostgreSQL.

- **Курсы и уроки:** MongoDB + PostgreSQL → outbox → OpenSearch/Elasticsearch и Redis. События `course_published` / `course_updated` обновляют индекс и сбрасывают карточку из кэша. Индекс может отстать на несколько секунд, что допустимо для поиска.

- **Прогресс:** PostgreSQL → outbox → ClickHouse. Каждое изменение прогресса публикуется как идемпотентное событие с `event_id`. ClickHouse строит воронки и агрегаты независимо от OLTP.

- **Форум:** PostgreSQL → outbox → ClickHouse / Redis. События модерации и активности поступают в аналитику; обновление темы инвалидирует кэш горячих обсуждений.

- **Логи:** клиент/сервисы → очередь или батч-обработчик → ClickHouse. Неблокирующая отправка защищает пользовательский сценарий. Повторные доставки устраняются потребителем по `event_id`.

- **Рекомендации:** ClickHouse (признаки) → плановый job → Redis. Пакетный расчёт записывает список для пользователя атомарно, с версией и TTL. Новые действия влияют на выдачу при следующем пересчёте.

## Общий механизм надёжности

Событие записывается в outbox в той же транзакции, что и изменение источника. Отдельный publisher отправляет его потребителям, а потребители хранят `event_id` для идемпотентности. Это снимает риск «данные изменились, а индекс не обновился» без распределённой транзакции.
